## 原因の切り分け

ローカルで両タイムゾーンの全テストを並行実行し、同じrename EPERMを再現しました。診断時に復元先subをlstatすると、リンクではない通常ディレクトリが残っていました。読み込み完了を待つ同期だけでも再現したため、単なる待ち時間不足として扱っていません。

Windowsのジャンクション作成は、通常ディレクトリを作り、ハンドルを開き、reparse pointを設定する複数段階の処理です。失敗時のディレクトリ削除も試みますが、その結果は保証されません。[libuvのWindows実装](https://github.com/libuv/libuv/blob/v1.x/src/win/fs.c)

旧テストは読み込み対象のsubでジャンクションを作成していました。途中の通常ディレクトリを保護された読み込みが開くと、作成や削除がロックされ、空ディレクトリが残る経路があります。旧コードは作成失敗を「攻撃がブロックされた」として復元へ進むため、占有されたsubへのrenameが繰り返し拒否されます。これはローカルの再現結果とlibuv実装から特定した原因で、GitHubジョブ内の途中状態を直接観測したものではありません。

## 改善したテスト方式

本体のソース読み込み、no-follow、共有モード、リンク拒否の保護は変更していません。変更対象はテストとその補助コード、文書だけです。

1. 読み込み対象外の専用パスで攻撃用リンクを完成させ、armedを通知します。準備失敗はテスト失敗です。
2. 元のsubをparkedへ移し、完成済みリンクをrenameでsubへ設置します。作成途中のディレクトリを読み込み対象に露出しません。
3. 攻撃状態を保持したまま、実際の保護された読み込みを実行します。全10ラウンド、計60回です。最初のラウンドは実際のリンク設置を必須とし、その状態での全読み込みの拒否を確認します。後続9ラウンドは読み込み開始と差し替え操作を重ね、信頼した内容以外が返らないことを確認します。OSによる攻撃操作の拒否は計測しますが、全ラウンドが拒否されて実際の攻撃を行わないテストは通りません。
4. 全読み込みの完了後にreleaseを通知します。その後だけリンクを対象パスから退避し、元ディレクトリを復元し、退避したリンク自体をunlinkします。再帰削除でリンク先へ進む処理はありません。
5. 復元完了通知を受け、最後に集計結果とワーカーの正常終了を待ちます。元ディレクトリのID・内容、外部の架空ファイルが変更されていないこと、一時リンクとparkedが残らないことも確認します。

復元時のロックに対する既存の回数制限付き再試行は維持し、制限を増やしていません。継続ロック、想定外エラー、通知欠落、不正なラウンド、異常終了はすべて失敗します。待機はタイムアウト付きです。テスト例外時にはワーカーの終了を待ってから一時フォルダの後片付けへ進みます。
