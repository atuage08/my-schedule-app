## 根本原因と再現

r3のquarantineTargetは復旧開始時に設定され、正常な読み戻しが終わっても残っていました。quarantine()が現在のrawよりこれを優先したため、別の破損Bへ更新しても、古いAを現在の破損データとして出力しました。書き込み失敗時も同様でした。

r3レビューZIPの展開コピーを変更せずに使い、独立レビューで提示された「A→復旧成功→B」と「A→書き込み失敗→B」の両条件で古いAが返ることを再現しました。本文や破損文字列はログに出さず、再現したかの真偽値だけを確認しました。独立レビューのテスト原本は提供されていないため、原本そのものの実行ではなく、提示された条件を回帰テストへ取り込んでいます。

## 状態の分離

| 状態 | 内容・寿命 |
| --- | --- |
| currentCorruption / observation | 最後に観測した現在の破損スナップショットと取得日時・ID。正常値・キー削除・読み取り不能では現在の破損対象を取り下げる |
| retainedRecoveries | 失敗・確認不能の復旧直前に保持した過去の文字列。現在のデータより優先して選ばない。ID・取得日時・最初の保持理由を持つ |
| protection | 書き込み結果が不確定なページの保護停止。観測・再描画・JSON準備では解除しない |

復旧の読み戻しまで成功したら、その破損状態を終了し、現在の破損対象と過去の復旧保持対象を終了します。保存キー削除後の緊急復旧成功も同様です。既に準備していた過去の保持ファイルは、その後のアプリ内保存操作で有効な保持対象とは扱いません。利用者が既に保存した外部ファイルを削除することはありません。

書き込み失敗では元のAを過去の保持対象として残し、現在のAと別に管理します。その後Bを観測した場合、現在の対象はB、過去の対象はAです。確認不能の場合はAを保持するとともに保護停止を維持し、観測したBがあっても編集・削除・完了・追加復元を再開しません。後から正常値を観測しても保護は解除しません。

同じ文字列を繰り返し保持する場合は最初の保持対象を再利用します。対象はデータのスナップショットであり、全試行の監査履歴ではありません。古い対象を自動破棄して容量を空けません。追加保持は最大8件・合計32MiBを超える新しい復旧の書き込みを拒否します。最初の対象は既存文字列への参照を保持するため、この追加保持の判定と分けています。.bin出力は従来どおり8MiB以下で、切り詰めません。

## 退避APIと画面

- quarantine()は現在の破損スナップショットだけを対象にし、過去の対象へフォールバックしません。
- retainedQuarantine(id)は明示的に選んだ過去の保持対象だけを対象にします。保護対象Aの取得にはこのAPIを使います。
- 現在の対象は準備直前に保存先を読み直し、生文字列と対象IDが一致した場合だけFileを作成します。不一致・正常値への変化・削除・読み取り不能なら出力を停止し、理由を表示します。
- 共有、ダウンロード、退避保存確認の直前もverifyQuarantineで再照合します。準備後に変わった現在対象を保存しません。
- 過去の対象も準備時と保存操作時に保存先との比較を試みます。不一致なら「現在とは異なる過去の対象」、読めなければ「一致確認不能」と明示します。過去のFileはその取得時点の内容としてだけ扱います。
- ファイル名にcurrent/retainedと対象IDを含めます。画面には取得日時と照合日時を表示します。.bin本文は従来のUTF-16LEコード単位のままで、HTMLとして表示せずログにも出しません。
- 準備済みの現在対象が古くなった場合は「現在ではない」と表示し、保存操作を停止します。復旧成功時には画面の退避準備・保存確認も終了します。
- 「保存先の状態だけを再確認」を用意しました。これは読み取りだけで、保護停止は解除せず、追加の書き込みもしません。
